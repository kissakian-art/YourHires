# YourHires project review

27 November 2026 · Current working tree on main, based on commit `c8d3a90`. The review includes the local changes and new files present in the workspace. Line references refer to this snapshot.

## Release decision

Hold a shared hosted rollout until tenant ownership, database backup access, and platform administrator bootstrap are fixed. For the Windows release, rebuild the embedded API before packaging. For existing installations, reconcile deposits, credits, return charges, and stock movements before relying on the dashboard totals. The findings below identify ways records can diverge. Establishing which customer records are affected requires a separate data review.

## Critical findings for shared hosting

| ID | Finding and evidence | Recommended fix and acceptance check |
|---|---|---|
| C1 | **Tenant ownership is disconnected from authentication.** Session lookup returns the user's company, but the global gate passes on the username. The company resolver trusts request data and defaults to company 1. Dispatch and invoice payment also load the target by ID alone. A user with a legitimate business role can act outside their company. See `server/src/server.ts:143, 857, 2004, 5721, 6450`. | Bind a tenant context once from the authenticated session. Scope reads, updates, and related-record lookups to it. Assign public bookings to the resolved storefront and verify every catalog line belongs to it. Check that two companies with identical role setups can each complete their own workflows and cannot read or change each other's records. |
| C2 | **Whole-database backup access crosses the tenant boundary.** Backup listing and download have no matching role rule or inline platform guard. Restore and deletion use tenant settings permission. The backup contains the entire database. In a shared deployment this exposes other businesses' records and gives tenant settings managers authority over installation-wide recovery. See `server/src/server.ts:239, 246, 1329, 1359, 1378` and `server/src/backup.ts:197`. | Make full backup administration platform-only on hosted installations, including listing and downloading. Keep desktop administration explicitly installation-scoped. Verify access for ordinary staff, tenant administrators, and platform operators, and run a restore drill on a disposable database. |
| C3 | **First-run platform administrator provisioning has an unsafe fallback.** On an installation without a superuser, bootstrap uses a source-defined password when configuration is absent. A matching pre-existing username is promoted without checking who owns it. See `server/src/server.ts:7039`. | Require explicit one-time setup credentials or an installation-local enrollment step. Stop on an existing-account collision. Verify both fresh setup and upgrading a database that already contains the configured username. Review existing installations for accounts created or promoted by this branch. |

## High-priority workflow defects

1. **A booking created with a deposit can get stuck before dispatch.** Internal booking creation records a positive deposit as paid and posts it to the ledger, but creates the booking as pending. In the bookings table, paid bookings lose the Collect action and only confirmed bookings get Dispatch. The confirmation handler also reposts the full deposit each time it runs. **Fix:** give deposit collection and booking confirmation explicit transitions, record each collection once, and allow a paid pending booking to advance without a second receipt. **Check:** a new paid-at-creation booking reaches dispatch through the UI with exactly one income entry and one ledger credit. See `server/src/server.ts:5605, 5619, 5665` and `client/src/App.tsx:5697, 5730`.

2. **Public bookings can leave rented stock available.** The public route stores the discriminator `Item`. Dispatch and return adjust bulk stock only for `item`. A public booking can therefore become an active rental without reducing available units. **Fix:** use a shared discriminator, normalize existing lines, and reconcile affected open orders against movement history before adjusting quantities. **Check:** send a public booking through confirmation, dispatch, and return. Three units out and back should produce exactly two opposing stock movements. See `server/src/server.ts:1831, 1860, 5794, 6155`.

3. **Dispatch can succeed operationally and fail financially.** Stock, the order, and booking conversion commit before the invoice and ledger debit. If billing fails, the caller receives an error and retry encounters an already converted booking. Concurrent dispatches also check conversion before entering the transaction. **Fix:** claim the booking conditionally and commit the order, inventory movements, invoice, and debit together, or persist a recoverable billing job with a unique order key. Use conditional stock updates. **Check:** interrupt billing and retry, then submit two simultaneous dispatches. Each booking must produce one order, one invoice, one debit, and one set of movements. See `server/src/server.ts:5724, 5738, 5830, 5852, 5864`.

4. **Partial returns overwrite earlier damage charges.** Fees are calculated from the current submission and replace the order total. Positive subsequent fees replace the earlier ledger debit and penalty invoice for the same order reference. A later clean return writes zero on the order while the previous invoice can remain payable. **Fix:** record each reconciliation as an immutable event, aggregate its charges, and issue explicit adjustments for already fiscalized invoices. **Check:** damage worth 100 followed by damage worth 40 must reconcile to 140 across the order, ledger, and invoices. A subsequent clean return must preserve that total. See `server/src/server.ts:1240, 6101, 6132, 6181, 6198` and `server/src/invoice-service.ts:248`.

5. **Payment posting can leave three different financial records.** The payment handler reads a balance, writes an absolute amount paid, then posts the ledger and income separately. Two payments can read the same balance. An income-write failure is logged and swallowed, allowing success with missing income. **Fix:** persist a uniquely identified payment and update the invoice, account, and income in one transaction with concurrency control. **Check:** two distinct payments of 30 against 100 leave 40 outstanding, replaying either leaves 40, and a failed income write leaves no partial posting. See `server/src/server.ts:1057, 1088, 6467, 6474, 6487, 6498`.

6. **Aging and dashboard totals misstate receivables.** Both queries select only Unpaid invoices and sum their face value. Recording a part-payment changes the status to Part Paid and drops the entire remaining balance from both reports. Conversely, an invoice created with a partial deposit stays Unpaid and contributes its full face value. **Fix:** derive a shared collectible balance from charges, cash, and credits, and use it for all open invoices. **Check:** an invoice for 100 with 30 collected must contribute 70 to the correct aging bucket and dashboard regardless of whether the 30 was a deposit or later payment. See `server/src/server.ts:6477, 6858, 6876, 6941, 6960` and `server/src/invoice-service.ts:198`.

7. **A fully credited invoice can still show a balance and accept payment.** A full credit changes status only. The formatter and payment endpoint subtract cash from face value without accounting for the credit. The UI hides the pay button, but its displayed balance comes from the formatter. Partial credits instead increment the cash-paid field. **Fix:** model credit allocations separately and enforce collectible balance in the posting transaction. **Check:** for a fully credited unpaid invoice of 100, the API and print view show zero due and the payment service rejects further collection. A partial credit must leave cash received unchanged. See `server/src/server.ts:6410, 6467`, `server/src/invoice-service.ts:369`, and `client/src/App.tsx:6039, 13602`.

8. **The Windows package can ship an older backend than its UI.** Tauri's prebuild compiles the frontend and packages an existing payload directory. Backend staging lives in a separate script. The staged backend on this checkout lacks the current fiscalization route, which is present in the fresh build. **Fix:** regenerate and verify the payload from the same revision within the release command. **Check:** build from a clean checkout and verify the installed app's API version, migration set, and fiscalization route before publishing the MSI. See `client/src-tauri/tauri.conf.json:10, 32`, `client/src-tauri/build-payload.sh:23`, and `server/src/server.ts:8342`.

## Additional operational defects

Reconciliation skips all consumables and rejects an empty reconciliation, leaving the order open through this workflow. See `server/src/server.ts:5533, 5550, 5560`. | Resolve the asset from its own catalog, preserve its ID, enforce quantity one, and claim availability at dispatch. | Purchase receipts | The handler increments stock on each transition into Received, permits arbitrary subsequent status changes, and reads the previous status before its transaction. Re-entering Received or concurrent receipts can increase stock twice. Dispatch uses the same number space for its reference and derives a unique invoice reference from it. Collisions can reject bookings or interrupt billing after dispatch. See `server/src/server.ts:5590, 5733, 1225` and `server/prisma/schema.prisma:340, 487`. | Allocate references in the database with an explicit company and period policy. Verify uniqueness under concurrency and calendar rollover. |

## Product and engineering gaps

- **Payment integrations.** The subscription UI explicitly simulates Stripe checkout. The project backlog also records Mobile Money as manual reference capture. Treat those as product decisions. If paid self-service is a release requirement, make verified provider events authoritative for upgrades, with duplicate-event handling and reconciliation. See `client/src/App.tsx:10142, 10255`, `server/src/server.ts:1750`, and `MISSING_FEATURES.md:245`.
- **Regression coverage.** Add disposable MySQL integration tests for the transaction and tenant cases above, plus browser tests for the paid-booking and public-booking journeys. Run them alongside builds, lint, schema validation, and migration tests on both empty and prior-version databases. Type checking passed despite the discriminator, status, and report mismatches.
- **Frontend maintenance.** Booking and invoice behavior spans a single large application component. Extract those screens alongside their regression tests. Review the dependency warnings in the affected effects and measure loading after splitting heavy screens. The bundle-size warning identifies a measurement target, not an observed user-facing delay.

## Recommended delivery order

1. **Before shared deployment:** close C1–C3, verify denial cases across two tenants, and review platform accounts and backup access history where records exist.
2. **Before the next billing cycle:** reconcile converted bookings against invoices and debits, deposits against income, credits against collectible balances, and return fees against their component events. Produce an exception list for operator review before adjusting historical records.
3. **For the next application release:** fix booking transitions and posting transactions first, then use the shared balance calculation in reports and printing. Add the stock, return, concurrency, and retry cases above as release checks.
4. **Before distributing the Windows build:** rebuild the payload, install the MSI on a clean machine, verify upgrade migrations on a copy of an existing database, and exercise a complete booking-to-payment journey.
